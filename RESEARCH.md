# Research

# Part 1 - Research
There was a lot I needed to consider for this project as I have not under taken a project like this before so there was a lot to learn. In the end I decided to use Python because of my small familiarity with it. I had not used Python in a long time, so my skills had faded. I also needed to learn how the different cyphers work so that I could ensure my code matches the exact function of them. Here are some of the websites I used to build my python knowledge:

- https://realpython.com/cheatsheets/python/ - An excellent reference point for while I was writing code
- https://pythonbynight.com/blog/starting-python-project - To get an idea of how I should go about structuring my code
- https://docs.python.org/3/library/random.html - To understand random.choice and random.randint for the guessing game

A lot of what you find online is not useful, and that becomes obvious quickly. Tutorials, Stack Overflow answers for a different problem, or cipher explanations with no code I could test. I built up a refence set of code and examples that I used to help me create the program.
I found the forums the most useful references. This is because there were other people asking similar questions, lost of comments and peer reviews, and they had also hit similar problems to me.

# Part 2 - Assessing information

When assessing information I used for research I asked myself:
1. Will this fit in to my code, does it help me achieve my program goals.
2. Do I understand what the code is doing, can I recreate it myself, and test it.
3. Is there an explanation covering the main points, is there good documentation.
4. Is The code correct, does it work.

If I could not answer these 4 I took what information I could from the example, but would then move on to a more developed example, or forum discussion.

# Part 3 - Problems

I quickly realised that my initial plan, which was to code a few different types of encryption and have a example for each of them much like the Caesar cypher,  may have been too ambitious. As when coming up with the plan I didn't grasp the full scale of the encoding required. This was obvious when I attempted to do Vigenère and enigma. This was beyond my current skill level and would take me far past the 3 hour recommended timeframe for this project, and it would have left me with unfinished code. Instead I replanned the program to use just one type of encryption, Caesar, and turn it into a game. It was the correct decision to adjust my project to fit into the timescales to achieve a similar goal.

Early versions of the code did not run correctly. The fist drafts had a missing menu and return functions which helped to navigate the code. There where also a few wrong operations which I did not realise as a problem until much later. Attempting to correct errors without reading the traceback was causing me problems, as at the time I did not know to do so. To rectify this, I systematically went through one functions at a time ensuring it all worked as intended.
 
# Part 4 - What I learned

I learned:
- Refamiliarizing myself with python is considerably faster with a "cheat sheet" and official docs.
- Structure makes understanding, finding, sorting and fixing code much easier. By preplanning and giving it a small title with reasonable gaps stops a mess being created before it even starts.
- Choosing a realistic and achievable target should always be done. Had I know what I was about to endeavour into I would have changed my whole plan before starting. It would have saved a considerable amount of time researching and testing code I don't understand.
- I should have a plan or an idea of how I will test my code. If I had considered this at the start I would have saved a lot of wasted time overcomplicating simple tasks.
- A major one is where and how to find good sources of example code. For python I can just go to the official Python forum and get up to date help on the specific code I need, Reddit also has many solutions however there is as much good as there is bad so being able to filter it is a useful skill.
 - I should have used more AI to help check the code and test. It would have saved a lot of time.
